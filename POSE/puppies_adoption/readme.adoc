= Ava.04 -- 🐶 Adoption Agency

You are going to build an application which allows an animal welfare organization to manage the admission and later adoption of puppies in multiple shelters.
See the <<sec:requirements,requirements>> sections for details.

In this assignment we will focus on two new aspects of desktop applications:

. Styling
. Directly accessing a database

== Styling

Avalonia allows for https://docs.avaloniaui.net/docs/basics/user-interface/styling/styles[several ways to style] your application.

. https://docs.avaloniaui.net/docs/basics/user-interface/styling/control-themes[WPF-like styles]
. CSS-like styles with classes
. Theme definitions which apply an overall look and feel to your application

We will focus primarily on the latter two, since they are a little saner.

NOTE: For the screenshots/sample run video I will apply only a theme and a changed font to keep it consistent.
You are, however, free to experiment with other styling techniques and the overall look -- let's see who creates the most beautiful application!

=== Resource Dictionaries

Resource dictionaries allow you to define static resources which can then be reused throughout your application.

.Colors.axaml
[source,xaml]
----
<ResourceDictionary xmlns="https://github.com/avaloniaui"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">
    <Color x:Key="PrimaryColor">#64B5F6</Color>
    <Color x:Key="SecondaryColor">#F6A564</Color>
    <Color x:Key="SurfaceColor">#FFFFFF</Color>
    <Color x:Key="SurfaceColorAlt">#000000</Color>
    <Color x:Key="HighlightColor">#C7E5F9</Color>
    <Color x:Key="ErrorColor">#EF5350</Color>
    <Color x:Key="SuccessColor">#66BB6A</Color>

    <SolidColorBrush x:Key="PrimaryBrush" Color="{StaticResource PrimaryColor}"/>
    <SolidColorBrush x:Key="SecondaryBrush" Color="{StaticResource SecondaryColor}"/>
    <SolidColorBrush x:Key="SurfaceBrush" Color="{StaticResource SurfaceColor}"/>
    <SolidColorBrush x:Key="SurfaceAltBrush" Color="{StaticResource SurfaceColorAlt}"/>
    <SolidColorBrush x:Key="HighlightBrush" Color="{StaticResource HighlightColor}"/>
    <SolidColorBrush x:Key="ErrorBrush" Color="{StaticResource ErrorColor}"/>
    <SolidColorBrush x:Key="SuccessBrush" Color="{StaticResource SuccessColor}"/>
</ResourceDictionary>
----

In this case several colors are defined and then brushes for them, which are needed to actually use them in the UI.
To make those resources available to the whole application, you need to include them in the `App.axaml` file:

.App.axaml
[source,xaml]
----
<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceInclude Source="avares://PuppyAdoption/Styles/Colors.axaml"/>
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>
----

=== CSS-like Styles

Inspired by CSS in the browser, you can define classes and apply one or more of them to a control.
Additionally, there are https://docs.avaloniaui.net/docs/reference/styles/pseudo-classes[pseudo-classes] like `pressed`, which work like in CSS as well.

.Buttons.axaml
[source,xaml]
----
<Styles xmlns="https://github.com/avaloniaui"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">
    <Style Selector="Button.primary"> <1>
        <Setter Property="Background" Value="{StaticResource PrimaryBrush}"/> <2>
        <Setter Property="Foreground" Value="{StaticResource SurfaceBrush}"/> <3>

        <Style Selector="^:pointerover /template/ ContentPresenter#PART_ContentPresenter"> <4><5>
            <Setter Property="Background" Value="{StaticResource HighlightBrush}"/> <6>
            <Setter Property="Foreground" Value="{StaticResource SurfaceAltBrush}"/> <6>
        </Style>
    </Style>

    <Style Selector="Button.secondary"> <7>
        <Setter Property="Background" Value="{StaticResource SecondaryBrush}"/>
        <Setter Property="Foreground" Value="{StaticResource SurfaceBrush}"/>

        <Style Selector="^:pointerover /template/ ContentPresenter#PART_ContentPresenter">
            <Setter Property="Background" Value="{StaticResource HighlightBrush}"/>
            <Setter Property="Foreground" Value="{StaticResource SurfaceAltBrush}"/>
        </Style>
    </Style>

    <Style Selector="Button.danger">
        <Setter Property="Foreground" Value="{StaticResource ErrorBrush}" />
    </Style>
</Styles>
----
<1> Defines a class `primary`, which can be applied to a `Button` control
<2> Sets the background color of the button to the primary color defined in the `Colors.axaml` resource dictionary
<3> Sets the foreground color of the button to the surface color defined in the `Colors.axaml` resource dictionary
<4> Defines a pseudo-class for when the button is hovered over -- `^` _repeats_ the outer selector, `Button.primary` in this case
<5> Because the theme adjusts not the button, but its content when hovering over it, we need to also target that, otherwise our changes would be overruled by the higher priority of the content style.
With `/template/` the content presentation template is accessed and then within that the `ContentPresenter` control is targeted -- you may treat these as 'magic variables' 😉
<6> Setting the background and foreground colors of the content presenter when the button is hovered over
<7> Defines a similar class `secondary` for buttons, which uses the secondary color instead of the primary one

To make those styles available to the whole application, you need to include them in the `App.axaml` file as well:

.App.axaml
[source,xaml]
----
<Application.Styles>
    <FluentTheme/>
    <StyleInclude Source="avares://PuppyAdoption/Styles/Buttons.axaml"/>
</Application.Styles>
----

Alternatively, you can include them in each `Window` or `UserControl` where you want to use them.

WARNING:  You will be fighting the theme all the time, which will often take precedence over your styles -- in complex ways where it targets a `Border` element within which has higher priority etc.
So if you really want to do a very custom styling, it might be a good idea to not use a theme at all, but instead define all component styles yourself.

The CSS-like style is then applied using the `Classes` property of the control:

.MainWindow.axaml
[source,xaml]
----
<Button Classes="primary">+</Button>
----

=== Themes

A good way to customize the overall look and feel of your application is to use a theme.
For this, we have two levels of complexity:

. Using the built-in fluent theme, but adjusting some colors
** Similar to what we did with Angular Material
. Creating a custom theme from scratch

Due to the unintuitive nature and complexity of doing a whole XAML theme, we will stick to the first option.
If you ever need to create a fully custom branded application, you'll have to get a designer on board and invest some serious time anyway.

A nice way to adjust the existing fluent theme -- which by default already has light & dark modes, adjusted to the OS theme automatically -- is to use the https://theme.xaml.live/[`FluentEditor` tool].
It allows you to quickly set a color palette to your liking and then generates the necessary XAML code for you.

== Database Access & General Architecture

While _in general_ accessing a database _directly_ from a desktop application, without an API in between, is a *bad idea*, many companies still have such setups to save cost (in the short term) by not having to implement an API at all.
Thus, we will do this _once_ as well.

Yet the infrastructure we need for this, will be mostly the same we need for a proper architecture -- especially dependency injection.
Later the services will perform calls to the backend instead of directly querying the database, but the rest will stay mostly the same (basically, the `Persistence` project would move to the backend).

Using _hosting_ of the .NET platform makes everything look and work very similar to ASP.NET Core, which you are already familiar with.
It provides things like processing of configuration & environment variables, logging and dependency injection.
I have prepared the infrastructure, but make sure you understand how things work together.
However, there are two noteworthy differences:

. No automatic environment handling (e.g. using the `.Development.json` config file(s))
** I solved this by using a preprocessor directive in the `Program.cs` file, which will set the environment to `Development` when running in debug mode
. The initial creation of a view model has to use the _service locator_ pattern
** Since there is no 'request' for which the framework could initiate the IoC chain for us, we have to do it manually
** Take a look at the `static T CreateViewModel<T>() where T : ViewModelBase` method I added in `App.axaml.cs`.
This will resolve the view model with its dependencies and then transitively all of their dependencies as well, so, except of having to call this method when requiring a view model, everything else then works as expected.

=== Lifetimes

It _usually_ does _not_ make sense to have _scoped_ services in a desktop application -- there are no requests or similar, independent tasks.
Typically, you will only have singletons and transient services.

*But*, because we are accessing the database directly, we face an additional problem: a `DbContext` can only be used for a _single_ request at once.
So if a user clicks a button while another query is still running, the application would crash.
To mitigate this, we will use one `DbContext` instance for each view model and then make sure to disable all interaction within that view model while a query is running.

One problem solved we face another: with _multiple_, long-lived (= as long as the view model exists) context instances, their *caches will start to diverge* and entities even loaded as tracking in one context will not be available in another => we always _have to keep that in mind and work around it_!

TIP: I left some code comments and will alert you in the instructions whenever we run into an issue caused by the multiple contexts

==== Disposing View Models

Because we have to use individual scopes for each view model, we also have to make sure those scopes are disposed of properly.
To automate this process, I created `ScopedWindow` & `ScopedControl` base class for our _views_ which automatically register an event handler that calls `DisposeAsync` on the view model, if the window is closed or the control is unloaded.

That is only necessary here, because we have the direct database access.
It would also be necessary with an API if you still need scoped view models for some other reason, but that should be very rare.

=== Design Facades

Our view models are now able to declare dependencies and the DI container will provide them automatically.

==== Image Processing

Because we have no backend, just the database, we have to do something we usually avoid: storing images directly in the database.
To ensure this doesn't blow up, we will limit the size of each image to a pixel size which almost guarantees to not exceed 100KB per image (which is fine with PostgreSQL https://www.postgresql.org/docs/current/storage-toast.html[TOAST]).

Yet we allow the user to select larger images as well as PNG files, but we do store appropriately sized JPEGs only.
To achieve this, some image processing is necessary -- and we already have everything we need, because Avalonia is built on top of https://skia.org/[Skia], the cross-platform graphics library that drives all the rendering you see in your application.
So `Bitmap` does not only *display* images, it also decodes, scales and encodes them: `CreateScaledBitmap` plus `Save` with `JpegBitmapEncoderOptions` is the whole job.

NOTE: We could reference https://github.com/mono/SkiaSharp[SkiaSharp] -- the .NET wrapper for Skia -- directly instead.
But then _we_ would pin one Skia version while Avalonia pins another, and the two have to agree, so every package update turns into a compatibility check.
Using what Avalonia already brings along avoids that problem entirely.

That is also why `ImageProcessor` sits in the client project and not in `Core`: `Core` is the layer that moves behind an API later on, and the image processing is going to stay right here.
It would run on a server just fine -- Skia does not care where it is hosted -- but scaling one photo is cheap on the machine of the user who picked it, while a server would be doing it for everybody.
So we deliberately spend the client's resources instead of the server's.

Make sure you take a good look at `ImageProcessor` -- and to make sure you do, I left a `TODO` as well 😉
That is also an excellent moment to try to understand how we configure the maximum pixel size using `appsettings.json` and access it via the familiar `IOptions`.
